## 2. Refactoring Opportunities

### A. ~~Path resolution duplicated everywhere~~ → ✅ Done
Every source file had its own `SCRIPT_DIR` / `PROJECT_DIR` / `CONFIG_PATH`. Extracted into shared `src/config.py` with `pathlib.Path`-based constants. All 10 source files now import from there.

### B. ~~Config loading duplicated in 7+ files~~ → ✅ Done
Single shared `load_config(path=None)` in `src/config.py`. All callers now delegate to it.

### C. ~~`fetch_router.py` uses subprocess~~ → ✅ Done
Replaced `subprocess.run(wikipedia_fetcher.py ...)` with direct import of `KiwixClient` + `load_fetcher_config`. Zero subprocess overhead. Tests rewritten to mock the class directly.

### D. ~~`orchestrator.py` duplicate section header~~ → ✅ Done (drive-by fix)

### E. `tts.py` prints to stderr instead of logging
Throughout `tts.py`, errors use `print(f"...", file=sys.stderr)` instead of `logger.error(...)`. Every other module uses the `logging` module consistently.

### F. `env_check.py` checks legacy `kiwix` config key but config uses `kiwix_servers`
The env check looks at `config.get("kiwix", {})` which no longer exists in your config.json (you use `kiwix_servers`). It will silently never reach the Kiwix connectivity check.

### G. `wikipedia_fetcher.py` has massive hardcoded constants
`SKIP_PATTERNS` (30+ entries across 7 languages) and `FOOTER_MARKERS` (8 entries) are hardcoded in the class. These could be config-driven or at least extracted to a data file for easy editing without touching code.

## 3. Doc/Code Inconsistencies

### A. `docs/orchestrator.md` shows pipeline as sequential, code runs TTS+Translate in parallel
The doc diagram says:
```
1. _fetch_and_clean()
2. _generate_tts()
3. _translate()
4. _extract_and_save_vocab()
5. delivery_callback()
```

But the actual `run_lesson()` does steps 3+4 (TTS + Translate) in **parallel** via `asyncio.gather()`. The doc should reflect this.

### B. `docs/orchestrator.md` mentions a `topic` parameter for `run_lesson()`
The doc shows:
```python
lesson = await orch.run_lesson("krystof", topic="Quantum Physics")
```
But `run_lesson()` signature is `(profile_name, delivery_callback=None)` — there's no `topic` parameter. The orchestrator always picks a random article; topics are only used by the news fetcher.

## 5. Architecture / Design Observations

### A. No shared config validation
Config shape is assumed everywhere. If someone puts `"schedule": {"time": "25:99"}` or forgets `telegram_chat_id`, the error surfaces deep in the pipeline with an obscure traceback. No centralized schema validation (e.g., pydantic).

### B. Orchestrator creates fresh instances of LlamaClient/Processor per call
`Orchestrator._get_llama_client()` and `_get_processor()` do lazy-init but are called on a fresh `Orchestrator(config=...)` each time the scheduler fires (see `scheduler.py:_worker()`). So there's no caching benefit across lessons. Minor, but worth noting if you ever need warm connections.

### C. Chat history DB has no cleanup/purge
`ChatHistoryDB.get_history()` limits to 10 turns, but old messages accumulate forever in SQLite. No TTL or max-size purge. Over months this grows unbounded per user.

## 6. Completed Work

### Daemon Crash Fix (2026-05-11)
- **`main.py`**: Fixed `TypeError: Passing coroutines is forbidden` — `self._wait_for_shutdown()` was a coroutine passed directly to `asyncio.wait()`, which requires explicit Tasks in Python 3.11+. Wrapped in `asyncio.create_task()`.
- **`scheduler.py`**: Fixed double-shutdown `SchedulerNotRunningError` on exit — added `.running` guard before calling `self._scheduler.shutdown()` in both `start().finally` and `stop()`.

### Scheduler Delivery Callback for Standalone Runs (2026-05-11)
- **`scheduler.py` CLI**: When `--run-now` or `--once` is used, the scheduler now wires up a `TelegramBot` delivery callback so lessons are actually sent via Telegram instead of just logged. Previously the standalone CLI had no way to deliver messages.

### requirements.txt Created (2026-05-11)
- **Created** `requirements.txt` with 6 direct dependencies and minimum version pins:
  - `aiogram>=3.28.0` — Telegram bot framework
  - `apscheduler>=3.11.0` — Cron-style scheduling
  - `beautifulsoup4>=4.14.0` — HTML cleaning (Wikipedia, news)
  - `feedparser>=6.0.0` — RSS feed parsing
  - `requests>=2.31.0` — HTTP client (KiwiX, RSS, fallback TTS)
  - `httpx>=0.28.0` — Async HTTP client (used by openai package)
  - `openai>=2.36.0` — LLM + TTS via OpenAI-compatible API
