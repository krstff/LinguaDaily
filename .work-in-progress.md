## 2. Refactoring Opportunities

### A. ~~Path resolution duplicated everywhere~~ → ✅ Done
Every source file had its own `SCRIPT_DIR` / `PROJECT_DIR` / `CONFIG_PATH`. Extracted into shared `src/config.py` with `pathlib.Path`-based constants. All 10 source files now import from there.

### B. ~~Config loading duplicated in 7+ files~~ → ✅ Done
Single shared `load_config(path=None)` in `src/config.py`. All callers now delegate to it.

### C. ~~`fetch_router.py` uses subprocess~~ → ✅ Done
Replaced `subprocess.run(wikipedia_fetcher.py ...)` with direct import of `KiwixClient` + `load_fetcher_config`. Zero subprocess overhead. Tests rewritten to mock the class directly.

### D. ~~`orchestrator.py` duplicate section header~~ → ✅ Done (drive-by fix)

### E. `tts.py` prints to stderr instead of logging
Throughout `tts.py`, errors use `print(f"...", file=sys.stderr)` instead of `logger.error(...)`. Every other module uses the `logging` module consistently.

### F. `env_check.py` checks legacy `kiwix` config key but config uses `kiwix_servers`
The env check looks at `config.get("kiwix", {})` which no longer exists in your config.json (you use `kiwix_servers`). It will silently never reach the Kiwix connectivity check.

### G. `wikipedia_fetcher.py` has massive hardcoded constants
`SKIP_PATTERNS` (30+ entries across 7 languages) and `FOOTER_MARKERS` (8 entries) are hardcoded in the class. These could be config-driven or at least extracted to a data file for easy editing without touching code.

### ~~H. `news_fetcher.py` FEED_CATALOGUE hardcoded~~ ✅ Done — moved to config.json

### H. Env check
Reevalute the importance of env check, is it used anywhere??
Get rid of legacy vocab file

### I. Profile management belongs in a web UI, not the Telegram bot
The Telegram bot currently handles `/register <profile>` to map chat IDs to profiles at runtime. This is fragile:
- No way to see all active mappings
- No way to edit or remove a profile's Telegram connection
- Multiple users could register to the same profile (last one wins)
- No persistence — mappings are lost when the daemon restarts

**Proposal**: Remove `/register` and all runtime profile management from the bot. Build a lightweight web UI for admin profile management:
- List all profiles with their Telegram chat IDs
- Add new profiles with language, schedule, source settings
- Edit existing profiles (schedule time, TTS voice, article filter)
- Connect/disconnect Telegram chat IDs to profiles
- Delete profiles
- Persist changes directly to `config.json`

## 5. Architecture / Design Observations

### A. No shared config validation
Config shape is assumed everywhere. If someone puts `"schedule": {"time": "25:99"}` or forgets `telegram_chat_id`, the error surfaces deep in the pipeline with an obscure traceback. No centralized schema validation (e.g., pydantic).

### B. Orchestrator creates fresh instances of LlamaClient/Processor per call
`Orchestrator._get_llama_client()` and `_get_processor()` do lazy-init but are called on a fresh `Orchestrator(config=...)` each time the scheduler fires (see `scheduler.py:_worker()`). So there's no caching benefit across lessons. Minor, but worth noting if you ever need warm connections.

### C. Chat history DB has no cleanup/purge
`ChatHistoryDB.get_history()` limits to 10 turns, but old messages accumulate forever in SQLite. No TTL or max-size purge. Over months this grows unbounded per user.

### D. Tutor chat crashes with read-only database error
Tutor chat breaks on any user message:
```
sqlite3.OperationalError: attempt to write a readonly database
```
Crash path: `tutor_catch_all` → `handle_tutor_message` → `self.db.add_message()` at line 91. The SQLite DB (`data/chat_history.db`) is likely mounted/written with read-only permissions (possibly a Docker volume or filesystem issue). Additionally, there may be a chat ID wiring problem — the bot appears to respond to the wrong user, suggesting `chat_id_to_profile` mapping isn't resolving correctly at runtime.

### SQLite + Chat History Hardening (2026-05-11)
- **`telegram_bot.py` ChatHistoryDB**: Added WAL journal mode (`PRAGMA journal_mode=WAL`) for better concurrent read/write performance; added `PRAGMA busy_timeout=5000` for multi-process robustness
- **Chat history TTL/purge**: Added `purge_old_entries(max_age_days=30)` method to prevent unbounded DB growth; auto-purges stale entries on bot startup
- **Graceful DB error handling**: Tutor chat wraps `add_message()` in try/except — DB write failures log a warning but don't block the reply to the user
- **Chat ID mapping logging**: `_build_mapping()` now logs each profile→chat_id mapping at INFO level, and profiles without `telegram_chat_id` at DEBUG level — makes runtime wiring visible in logs

### TTS Logging Fix (2026-05-11)
- **`tts.py`**: Replaced all 4 `print(..., file=sys.stderr)` calls with proper `logger.warning()` / `logger.error()` calls. Now consistent with every other module.

### Test Suite Green (2026-05-11)
- **Fixed 13 failing tests** → all **173 passing**:
  - **4 scheduler tests**: `_build_job()` now enqueues instead of running directly — rewrote to use `scheduler.run_once()` exercising the full enqueue→worker cycle
  - **6 news_fetcher tests**: MagicMock `.get()` returns mocks, not set attrs — configured `.get.side_effect` with dict lookup lambdas; fixed bare `Exception` → `requests.RequestException`
  - **2 news_fetcher truncation tests**: `_filter_article` couldn't truncate single-paragraph text — added word-level fallback in source
  - **1 processor test**: monkeypatched `__file__` but code uses `config.PROJECT_DIR` — patched `cfg.PROJECT_DIR` instead
  - **1 wikipedia test**: Test data had no section fitting min/max — adjusted word counts

### Daemon Crash Fix (2026-05-11)
- **`main.py`**: Fixed `TypeError: Passing coroutines is forbidden` — `self._wait_for_shutdown()` was a coroutine passed directly to `asyncio.wait()`, which requires explicit Tasks in Python 3.11+. Wrapped in `asyncio.create_task()`.
- **`scheduler.py`**: Fixed double-shutdown `SchedulerNotRunningError` on exit — added `.running` guard before calling `self._scheduler.shutdown()` in both `start().finally` and `stop()`.

### Scheduler Delivery Callback for Standalone Runs (2026-05-11)
- **`scheduler.py` CLI**: When `--run-now` or `--once` is used, the scheduler now wires up a `TelegramBot` delivery callback so lessons are actually sent via Telegram instead of just logged. Previously the standalone CLI had no way to deliver messages.
