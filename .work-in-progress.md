## 2. Refactoring Opportunities

### A. Path resolution duplicated everywhere (~10 files)
Every source file has this block:
```python
SCRIPT_DIR = os.path.dirname(os.path.abspath(__file__))
PROJECT_DIR = os.path.join(SCRIPT_DIR, "..")
CONFIG_PATH = os.path.join(PROJECT_DIR, "config.json")
```

**Proposal**: Extract into a shared `src/config.py` or `src/paths.py`:
```python
# src/paths.py
import pathlib
PROJECT_DIR = pathlib.Path(__file__).resolve().parent.parent
CONFIG_PATH = PROJECT_DIR / "config.json"
DATA_DIR = PROJECT_DIR / "data"
```

### B. Config loading duplicated in 7+ files
`_load_config()` or `load_config()` appears independently in: `scheduler`, `orchestrator`, `telegram_bot`, `llama_client`, `tts`, `fetch_router`, `wikipedia_fetcher`, `main`. All do the same thing (open JSON, load, return dict).

**Proposal**: One shared `load_config(path=None)` in `src/config.py`. Already exists in `orchestrator.py` but isn't reused elsewhere.

### C. `fetch_router.py` uses subprocess to call `wikipedia_fetcher.py`
The fetch router spawns a **subprocess** of `wikipedia_fetcher.py` and parses JSON stdout, instead of just importing and calling it directly:
```python
# fetch_router._fetch_wikipedia() — current approach
result = subprocess.run(
    [sys.executable, "wikipedia_fetcher.py", "--config", ...],
    capture_output=True, text=True, timeout=60
)
data = json.loads(result.stdout)
```

**Why this is problematic:**
- 60-second subprocess timeout (lesson pipeline can silently fail)
- Can't share state (sessions, config objects) — re-initializes everything
- Harder to test (requires mocking subprocess, not a function call)
- Cross-language fetchers (news) use direct imports, Wikipedia uses subprocess — inconsistent

**Proposal**: Replace with direct import: `from wikipedia_fetcher import KiwixClient` and instantiate directly. Same result, zero subprocess overhead.

### D. `orchestrator.py` has duplicate section header
Line ~103-104:
```python
# ── Article fetching wrapper ────────────────────────────────────────

# ── Article fetching wrapper ────────────────────────────────────
```
The comment appears twice. Minor but sloppy.

### E. `tts.py` prints to stderr instead of logging
Throughout `tts.py`, errors use `print(f"...", file=sys.stderr)` instead of `logger.error(...)`. Every other module uses the `logging` module consistently.

### F. `env_check.py` checks legacy `kiwix` config key but config uses `kiwix_servers`
The env check looks at `config.get("kiwix", {})` which no longer exists in your config.json (you use `kiwix_servers`). It will silently never reach the Kiwix connectivity check.

### G. `wikipedia_fetcher.py` has massive hardcoded constants
`SKIP_PATTERNS` (30+ entries across 7 languages) and `FOOTER_MARKERS` (8 entries) are hardcoded in the class. These could be config-driven or at least extracted to a data file for easy editing without touching code.

## 3. Doc/Code Inconsistencies

### A. `docs/orchestrator.md` shows pipeline as sequential, code runs TTS+Translate in parallel
The doc diagram says:
```
1. _fetch_and_clean()
2. _generate_tts()
3. _translate()
4. _extract_and_save_vocab()
5. delivery_callback()
```

But the actual `run_lesson()` does steps 3+4 (TTS + Translate) in **parallel** via `asyncio.gather()`. The doc should reflect this.

### B. `docs/orchestrator.md` mentions a `topic` parameter for `run_lesson()`
The doc shows:
```python
lesson = await orch.run_lesson("krystof", topic="Quantum Physics")
```
But `run_lesson()` signature is `(profile_name, delivery_callback=None)` — there's no `topic` parameter. The orchestrator always picks a random article; topics are only used by the news fetcher.

## 5. Architecture / Design Observations

### A. No shared config validation
Config shape is assumed everywhere. If someone puts `"schedule": {"time": "25:99"}` or forgets `telegram_chat_id`, the error surfaces deep in the pipeline with an obscure traceback. No centralized schema validation (e.g., pydantic).

### B. Orchestrator creates fresh instances of LlamaClient/Processor per call
`Orchestrator._get_llama_client()` and `_get_processor()` do lazy-init but are called on a fresh `Orchestrator(config=...)` each time the scheduler fires (see `scheduler.py:_worker()`). So there's no caching benefit across lessons. Minor, but worth noting if you ever need warm connections.

### C. Chat history DB has no cleanup/purge
`ChatHistoryDB.get_history()` limits to 10 turns, but old messages accumulate forever in SQLite. No TTL or max-size purge. Over months this grows unbounded per user.

## 6. Completed Work (2026-05-10)

### Serial FIFO Queue for Scheduler
- Replaced direct cron→run with cron→enqueue→single worker pattern
- All lessons now run sequentially, no overlap even when profiles share the same time
- Removed `max_instances=1` (no longer needed — queue handles serialization)

### CLI Debug Flags
- `--once` / `-o`: Run all scheduled profiles once and exit (testing)
- `--run-now` / `-n`: Push all profiles onto queue immediately, then stay alive as daemon
- Both exposed in the programmatic API: `scheduler.run_once()` and `scheduler.start(immediate_run=True)`

### Docs Updated
- `docs/scheduler.md`: Architecture diagram, queuing behavior section, CLI flags table, Import API
- `README.md`: Testing section now includes `--once` and `--run-now` examples
